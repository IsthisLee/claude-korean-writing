# 주입이 일을 방해하는가

> 2026-09-11 에 상시 주입과 서브에이전트 주입을 뺐다([EVALUATION.md](../../../EVALUATION.md) H13). 이 폴더는 그 전의 기록이다. B 조건은 지운 `plugin/hooks-handlers/sessionstart.sh` 를 부르므로 지금 저장소로는 다시 돌릴 수 없다.

이 플러그인은 세션마다, 그리고 서브에이전트마다 한국어 규칙을 컨텍스트에 넣습니다.
저장소의 다른 측정은 전부 **글이 좋아졌는가**를 봅니다. 여기서 보는 것은 반대쪽입니다.
**규칙을 넣어서 모델이 일을 덜 잘하게 되지 않았는가.**

문체는 채점하지 않습니다. 답이 맞았는지, 시킨 대로 했는지만 봅니다.

## 무엇을 재나

| 시험 | 묻는 것 | 채점 |
| --- | --- | --- |
| 정확도 | 기술 문제의 정답률이 주입 때문에 떨어지는가 | 답이 하나로 떨어지는 문제 10개. `ANSWER=` 문자열 비교 |
| 지시 준수 | 규칙과 반대되는 것을 사용자가 명시로 요청하면 누구를 따르는가 | 이모지·불릿·번호·영어를 실제로 냈는지 |
| 코드 품질 | 주입이 경계 조건 처리를 떨어뜨리는가 | 모델이 쓴 함수를 **실제로 돌려** 숨은 테스트에 넣는다 |
| 설계 능력 (짧은) | 주입이 짚어야 할 개념을 떨어뜨리는가 | 빠지면 설계가 틀리는 개념 여덟이 나왔는지 센다 |
| 설계 능력 (장문) | 빠짐없이 늘어놓아야 하는 과제에서도 그런가 | 개념 열여섯. **길이 게이트**가 여기 붙어 있다 |
| 코드 리뷰 | 주입이 결함 검출을 떨어뜨리는가 | 심어 둔 결함 다섯 개 중 몇 개를 찾는지 |
| 정보 보존 | 요약이 원문의 사실을 떨어뜨리는가 | 원문의 사실 열두 개 중 몇 개가 남는지 |
| 과잉 단정 | 정보가 없을 때 없다고 말하는가 | 정보 부족을 밝혔는지, 무엇을 봐야 하는지 짚었는지 |
| 디버깅 | 주입이 원인 지목을 흐리는가 | 원인이 되는 줄 번호를 맞혔는지 |
| 서브에이전트 | 주입이 조사 결과를 흐리거나 답변 언어를 끌어당기는가 | 저장소에서 값을 찾아오게 하고 정답과 한글 비중 |
| 스킬 오발동 | 코드 작업에서 글 작성 스킬이 잘못 뜨는가 | 스트림에서 `Skill` 호출을 센다 |

설계 답을 사람이 읽고 견주면 문체에 끌립니다. 주입을 받은 쪽은 불릿과 소제목이 없어 같은 내용이라도
다르게 읽힙니다. 그래서 개념이 나왔는지만 셉니다. 표현이 어떻든 짚었으면 맞은 것입니다.
길이도 같이 냅니다. 규칙이 글을 짧게 만들어 개념이 덜 나왔다면 그것도 저하이기 때문입니다.

**길이 게이트가 이 실험의 조기 경보입니다.** 개념 적중은 표본이 많이 필요해서 늦게 움직입니다.
그보다 먼저 무너지는 것이 길이입니다. 주입을 받은 쪽의 길이 중앙값이 주입 없는 쪽의 85% 아래로
내려가면 `grade_design.py` 가 종료 코드 1 을 내고 `run_all.sh` 도 같이 실패합니다.
개념 적중이 아직 안 갈렸어도 그 앞단이 무너진 것으로 봅니다.

코드는 읽고 판단하지 않고 실행합니다. 숨은 테스트에는 빈 입력, 맞닿는 구간, 안정 정렬,
멀티바이트 글자, 루트 위로 올라가는 `..` 이 들어 있습니다. `python3 code_tests.py --self` 로
참조 구현을 넣어 테스트 자체가 맞는지 먼저 봅니다.

지시 준수는 이 플러그인에서 가장 중요한 안전장치입니다. 주입문은 이모지를 쓰지 말라고,
`첫째·둘째` 병렬을 쓰지 말라고 적습니다. 사용자가 그것을 달라고 하면 **사용자가 이깁니다.**
그 확인이 여기 있습니다.

스킬 오발동에는 **양성 대조**가 붙어 있습니다. 진짜 글 작성 요청 하나를 같이 돌려
검출기가 실제로 스킬 호출을 잡는지 봅니다. 그것이 0 이면 나머지 0 은 근거가 아닙니다.

## 어떻게 재나

```bash
docs/experiments/task-performance/run_all.sh     # 여섯을 한 번에
python3 docs/experiments/task-performance/code_tests.py --self   # 테스트 자체가 맞는지
```

주입을 켠 판(B)과 끈 판(A)으로 같은 프롬프트를 돌려 붙입니다. 정확도는 작은 모델과 큰 모델
두 곳에서 봅니다. 큰 모델은 대부분 만점이라 저하가 있어도 안 보이므로 여유가 있는 쪽을 같이 둡니다.

주입은 저장소의 실제 훅(`plugin/hooks-handlers/sessionstart.sh`)을 부릅니다. 서브에이전트 쪽은
플러그인을 통째로 얹고 `KOREAN_WRITING_SUBAGENT_DISABLED` 로 가릅니다.

이미 있는 결과는 건너뜁니다. 중간에 끊고 다시 돌려도 됩니다. 산출물은 `out/`·`subout/`·`skillout/`
에 쌓이고 커밋하지 않습니다. `grade.py` 가 채점하고 `run_all.sh` 가 마지막에 부릅니다.

LLM 을 부르므로 CI 에 넣지 않습니다. `plugin/hooks-handlers/always-on.md` 를 고쳤으면 릴리스 전에 돌립니다.

## 결과 (2026-09-11)

**정확도는 갈리지 않았습니다.**

| 모델 | A 주입 없음 | B 주입 있음 | 차이 95% 구간 |
| --- | --- | --- | --- |
| Haiku 4.5 | 40/40 | 39/40 | −11.5 ~ +7.9%p |
| Opus 5 | 30/30 | 29/30 | −15.0 ~ +10.0%p |

틀린 두 건은 각각 다른 문항이고 같은 문항의 다른 표본은 맞혔습니다. 표본 흔들림입니다.

**구간이 넓다는 것을 그대로 적습니다.** 두 조건이 거의 만점이라 이 표본이 배제하는 것은
**10%p 를 넘는 저하**뿐입니다. 그보다 작은 저하가 없다고는 말할 수 없습니다.
표본을 늘리는 것보다 여유가 있는 과제를 찾는 쪽이 먼저입니다.

**사용자 지시가 규칙을 이깁니다.** 25건 가운데 25건입니다. 이모지를 넣어 달라고 하면 넣고,
`첫째·둘째·셋째`로 달라고 하면 그렇게 쓰고, 영어로 답하라고 하면 영어로 답합니다.
주입을 끈 쪽이 오히려 이모지 요청 다섯 중 둘을 빠뜨렸습니다.

**서브에이전트도 갈리지 않았습니다.** 양쪽 6/6 입니다. 영어로 답하라고 한 과제에서
한글 비중은 양쪽 다 2% 이하입니다. 다만 표본이 조건당 셋이라 구간이 아주 넓습니다.

**스킬은 잘못 뜨지 않았습니다.** 코드 작업 8건에서 양쪽 다 0건이고 양성 대조에서는 1건입니다.
주입문이 "글 작성 요청은 스킬을 먼저 로드한다"고 지시하는데도 코드 작업을 글 작성으로 읽지 않습니다.

**설계에서는 저하가 나왔고, 고쳤습니다.** 이것이 이 실험에서 나온 유일한 실제 신호입니다.

| 판 | 개념 적중 | 답변 길이 중앙값 | A 와의 차이 95% 구간 |
| --- | --- | --- | --- |
| A 주입 없음 | 151/160 (94%) | 4,884자 | 기준 |
| v1 옛 주입문 | 140/160 (88%) | 3,906자 | **[−13.2, −0.3]%p** |
| v2 분량 방어 한 줄 | 143/160 (89%) | 4,531자 | [−11.1, +1.3]%p |
| v3 서식 범위 축소 | **148/160 (92%)** | **4,909자** | [−7.6, +3.9]%p |

옛 주입문에서는 구간이 0 을 벗어났습니다. 설계 답변이 20% 짧아지고 짚어야 할 항목이 빠졌습니다.

두 번에 걸쳐 고쳤습니다. 먼저 `규칙은 표현을 고르는 기준이다. 짚어야 할 내용을 빼거나 분량을
줄이는 데 쓰지 않는다.` 를 넣었고 길이가 4,531자로 돌아왔습니다. 그래도 점 추정이 −5.0%p 로
남아서 주입문을 다시 봤더니 서식 금지가 조건 없이 전부에 걸리고 있었습니다. 코드와 로그는 빼
두었는데 기술 답변의 목록과 절차는 빼지 않았습니다. 적용 범위를 **사용자에게 내는 산문**으로
좁히니 길이가 4,909자로 주입 없는 쪽과 같아지고 적중이 92% 가 됐습니다.

**코드 품질은 이 과제로 가리지 못합니다.** Opus 120/120 대 120/120, Haiku 160/160 대 160/160 입니다.
차이가 없다고 읽으면 안 됩니다. 과제가 쉬워서 안 보이는 것입니다. 더 어려운 과제가 필요합니다.

**드는 것은 토큰뿐입니다.** 총입력 중앙값이 3,655 에서 4,381 로 726 늘었습니다(옛 주입문 기준).
새 주입문은 784 입니다. 출력 길이와 걸린 시간은 갈리지 않았습니다.

**짧아지지만 내용은 남습니다.** 주입을 받은 쪽이 대체로 짧습니다. 리뷰 1,172자 대 928자,
요약 1,320자 대 1,030자입니다. 그런데 결함 검출과 사실 보존은 갈리지 않았습니다.
설계와 다른 점이 여기입니다. 설계는 열거할 항목이 많아 짧아지면 빠지고, 리뷰와 요약은
항목이 정해져 있어 짧아져도 남습니다.

**표본 셋으로 멈췄으면 없는 저하를 보고할 뻔했습니다.** 리뷰가 표본 셋일 때 Haiku 에서
90% 대 83% 로 −7%p 였습니다. 여덟로 늘리니 −1.3%p 가 됐습니다.

**측정 도구를 두 번 고쳤습니다.** 정보 보존과 과잉 단정의 첫 판이 통째로 무효였습니다.
도구를 없앤 세션에서 모델이 도구 호출 텍스트를 내고 끝났고, 실행 위치가 이 저장소라
저장소를 뒤지려 들었습니다. 채점기가 그것을 0 점으로 세서 「정보 보존 89% 대 20%」라는
가짜 저하가 나왔습니다. 프롬프트에 도구가 없다는 것을 적고, 빈 디렉터리에서 돌리고,
채점기가 오염된 표본을 세지 않고 이름을 찍어 알리도록 고쳤습니다.

## 이 실험이 못 보는 것

- **긴 작업.** 여기 과제는 한 턴에서 끝납니다. 스무 턴짜리 코딩 작업에서 규칙이 판단을 흐리는지는 재지 않았습니다.
- **작은 저하.** 위에 적은 대로 10%p 아래는 가리지 못합니다.
- **도구 사용.** 정확도 시험은 도구를 끄고 돌립니다. 도구를 고르는 판단에 주입이 영향을 주는지는 별개 문제입니다.
- **코드 과제의 난이도.** 두 모델 다 만점이라 가리는 힘이 없습니다.
- **설계의 옳고 그름.** 개념이 나왔는지만 셉니다. 그 개념을 옳게 썼는지는 보지 않습니다.
- **큰 모델의 천장.** 리뷰·보존·디버깅이 Opus 에서 만점이라 가리는 힘이 약합니다.
- **정직함의 진위.** 과잉 단정은 표현이 있었는지로 셉니다. 그 표현이 진짜 판단이었는지는 모릅니다.
